🏗 АРХИТЕКТУРНЫЙ МАНИФЕСТ ПРОЕКТА (FLORIFY)

Стек: Java 21, Spring Boot 3.4, PostgreSQL, Kafka, Redis, MapStruct, Flyway.
Архитектура: Модульный Монолит со строгой Гексагональной Архитектурой (Ports & Adapters) внутри доменов. Все модули используют единую базу данных и схему public для упрощения консолидации.

💎 1. БАЗОВЫЕ ПРАВИЛА КОДА (Анти-Бойлерплейт)
Наша цель — писать выразительный код, используя мощь Java 21, и не тащить легаси-практики.

- **Везде record по умолчанию**: Все DTO (Request/Response), Команды (Commands), События (Events) и иммутабельные Доменные объекты (Value Objects) обязаны быть нативными Java record. Использование Lombok (@Value, @Builder, @Data) для них СТРОГО ЗАПРЕЩЕНО.
- **Никакого ручного маппинга**: Запрещено писать методы конвертации вроде `public static Response from(Entity e)` внутри DTO или контроллеров. Весь маппинг между слоями (Domain ↔ DTO, Domain ↔ JpaEntity) выполняется ИСКЛЮЧИТЕЛЬНО через MapStruct.
- **Обязательное условие**: Все мапперы должны иметь аннотацию `@Mapper(componentModel = "spring")`.
- **Правила использования Lombok**:
    - Lombok разрешен только там, где Java record физически не подходит (JPA-сущности, изменяемые Rich Domain Objects).
    - **АННОТАЦИЯ @Data СТРОГО ЗАПРЕЩЕНА ВО ВСЕМ ПРОЕКТЕ**. Она ломает работу с коллекциями в Hibernate (из-за генерации equals/hashCode по всем полям). Используйте только `@Getter` и `@Setter`.
    - Для конструкторов используем `@RequiredArgsConstructor` (для инъекции зависимостей) и `@AllArgsConstructor`.
- **Владение временем**: Слои Адаптеров и БД не генерируют время. `Instant.now()` вызывается строго в слое Application при создании доменной сущности. Сущности должны быть независимыми от хуков базы данных (запрет на `@PrePersist`/`@PreUpdate`).

🏛 2. ЧИСТАЯ ГЕКСАГОНАЛЬНАЯ АРХИТЕКТУРА (Глубокий разбор)
Главное правило проекта — Правило Зависимостей (Dependency Rule). Зависимости всегда направлены внутрь. Слой Domain ничего не знает об Application. Слой Application ничего не знает об Adapters и фреймворках (REST, JPA, Kafka).

🟢 2.1 Слой Domain (domain/)
Сердце системы. Содержит только чистую бизнес-логику, правила и состояния.
- **Что внутри**: Доменные модели (Product), Сущности с состоянием (StockBalance), Доменные события (StockWrittenOffEvent), Специфичные эксепшены (DomainException).
- **Ограничения**:
    - Строгий 0 импортов `org.springframework.*`.
    - Строгий 0 импортов `jakarta.persistence.*`.
    - Никаких ссылок на БД, JSON или HTTP.
- **DDD Идентичность**: Если класс является Entity (имеет жизненный цикл и ID), он обязан иметь `@EqualsAndHashCode(onlyExplicitlyIncluded = true)` над классом и `@EqualsAndHashCode.Include` строго над полем id.

🟡 2.2 Слой Application (application/)
Дирижер бизнес-процессов. Содержит сценарии использования (Use Cases) и контракты (Порты) для связи с внешним миром.
- **Что внутри**: Команды (CreateProductCommand), Интерфейсы UseCase (port/in/), Интерфейсы для БД/Сообщений (port/out/), Интеракторы (service/).
- **Ограничения (Анти-протечка инфраструктуры)**:
    - Слой имеет право использовать Spring Core (`@Service`, `@Transactional`), но КАТЕГОРИЧЕСКИ ЗАПРЕЩАЮТСЯ импорты из пакета `adapter/`.
    - **Spring Data BAN**: Запрещено использовать `org.springframework.data.domain.Pageable` или `Page<T>` в портах out/. Слой Application должен использовать чистые примитивы (int page, int size) и возвращать кастомный `PagedResult<T>`.

🔴 2.3 Слой Adapters (adapter/)
Грязный внешний мир. Точки входа и выхода из системы.

🚪 Входящие адаптеры (adapter/in/)
То, что вызывает наше приложение (REST Контроллеры, Kafka Consumers, Scheduler).
- **Контроллеры не содержат бизнес-логики**. Их задача: принять HTTP, вызвать MapStruct, дернуть метод UseCase (через интерфейс, а не реализацию) и отдать ответ.
- **Строгое соблюдение HTTP-семантики**: 201 Created для создания, 204 No Content для пустого ответа, 200 OK для запросов с телом, 409 Conflict для нарушений уникальности.
- **Аутентификация и извлечение userId (performerId)** происходит на уровне REST (через `@AuthenticationPrincipal`), чтобы клиент не мог подделать свой ID.

🔌 Исходящие адаптеры (adapter/out/)
То, что наше приложение вызывает (БД, Kafka Publishers, Redis, Внешние API).
- Только здесь живут JPA-сущности (*JpaEntity.java) и репозитории (*JpaRepository.java).
- Адаптер имплементирует интерфейс из port/out/.
- Именно адаптер берет на себя грязную работу: получает int page, int size от слоя Application, оборачивает их в спринговый PageRequest, идет в БД и маппит результат обратно в чистый PagedResult.

🔐 3. БЕЗОПАСНОСТЬ И КОНТРОЛЬ ДОСТУПА
- Все эндпоинты (кроме публичных) обязаны быть защищены аннотацией `@PreAuthorize("hasAnyRole(...)")`.
- Ролевая модель строгая: каждый домен (модуль) сам решает, какие роли имеют доступ к его UseCase.
- CORS настраивается централизованно через `SecurityConfig` с использованием `CorsConfigurationSource` (запрет на глобальный * для production-урлов).

💽 4. БАЗЫ ДАННЫХ И ТРАНЗАКЦИИ (JPA & Flyway)
- **Миграции обязательны**: Изменение структуры БД происходит только через скрипты Flyway (V1__...sql). `spring.jpa.hibernate.ddl-auto` строго в режиме `validate`.
- **Оптимистичные блокировки**: Любая изменяемая сущность (Product, StockBalance) ОБЯЗАНА иметь поле version INTEGER (и в БД, и в Entity, и в Домене) для защиты от потерянных обновлений.
- **Append-Only история**: Транзакционные таблицы (например, движения по складу) работают только на INSERT. Изменять исторические записи запрещено (на них не вешается `@Version`).
- **Идемпотентность БД**: Все входящие документы/запросы должны проверяться на дубли через уникальные индексы в БД (например, UNIQUE(source_document_id)).

📨 5. МЕЖДОМЕННЫЕ СООБЩЕНИЯ (Kafka и Spring Events)
Развертывание системы происходит как **Модульный Монолит (Modular Monolith)** (все домены живут в 1 JVM и используют одну схему базы данных public).

- **Новая логика (Spring Events):** Для нового асинхронного междоменного взаимодействия предпочтительно использовать внутреннюю шину `Spring ApplicationEventPublisher` в связке с `@Async` и виртуальными потоками (Virtual Threads). Это дает скорость памяти без JSON-сериализации. Домены остаются decoupled — общаются строго через DTO-события.
- **ОБРАТНАЯ СОВМЕСТИМОСТЬ (Kafka):** Уже существующая логика (Outbox, Scheduler, Debezium), написанная с использованием Kafka, ПРИЗНАЕТСЯ ВАЛИДНОЙ. **СТРОГО ЗАПРЕЩАЕТСЯ переписывать существующую рабочую логику с Kafka на Spring Events**, если в ней нет багов. Kafka остаётся в инфраструктуре.
- При использовании Kafka сохраняются правила: Exactly-Once семантика (`ENABLE_IDEMPOTENCE_CONFIG = true`), `ErrorHandlingDeserializer` для предотвращения Poison Pill, Keys = ID сущности для сохранения порядка.
